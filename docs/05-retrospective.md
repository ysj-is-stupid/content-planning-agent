# 项目复盘

更新：2026-11-06。

## 1. 实际投入与完成范围

从需求澄清、技术选型、核心实现、失败调试、真实模型复测到交付材料整理，累计投入约 6 小时以上。该数字为整个过程的区间估算，不记录精确起止时间；实际投入超过建议的三小时范围，增加的工作主要用于持久化恢复、额度边界、在线对照实验和交付审查整改。

核心链路、真实模型决策循环、预算重规划、工具失败调整、幂等、费用守卫和完整结果聚合已经完成。生产级多 worker、真实外部副作用对账、开放内容质量和跨版本自动迁移不在本次完成范围内。

## 2. 最难的问题

### 动态决策与确定性守卫的边界

最容易做成的是程序发现超预算后直接切换便宜方案，但这不能证明模型观察结果后做了新决策。最终实现让模型每轮只选择一个动作，程序只负责验证和执行；预算 10 与预算 20 的真实模型对照分别产生“改图文”和“直接保存”，从 Trace 而不是预设日志证明差异。

### checkpoint 与业务事实并不原子

LangGraph checkpoint 不能保证工具副作用恰好一次。项目额外使用 SQLite 操作意图、回执、attempt、唯一收费记录和保存事务，把业务库作为权威，并针对业务已提交但 checkpoint 尚未落盘的窗口做恢复测试。这个问题比搭建状态图本身更耗费设计和调试时间。

### 费用、依赖与状态必须同时正确

只算出总额不够。方案更换后旧脚本和报价可能失效，已发生的工具费用又必须保留；失败调用不能标成功，最终完成还必须有数据库保存记录。因此采用不可变方案版本、依赖指纹、内容哈希、报价绑定和保存时重新校验，避免状态表面完成但引用已经陈旧。

### 证据必须与实现一致

离线 Mock 可以稳定覆盖边界，但不能证明真实模型会调整计划；真实模型 Trace 又可能因提示词、检索行为或模型波动失败。项目保留首次失败与提示修正过程，并把离线流程测试、真实模型行为和文档结论分开表述。

## 3. 学习与收获

1. Agent 项目的核心不是调用模型，而是定义模型能决定什么、程序必须保证什么，以及失败后哪些事实仍然可信。
2. checkpoint、重试和幂等是不同问题；自动重试只能处理已知安全的瞬时错误，不能代替业务重规划或外部结果对账。
3. 预算、时间和产物引用应尽量使用不可变、可重算的数据，而不是采信模型给出的成功状态或旧可行性结论。
4. 真实模型评估需要成对条件、失败样本和明确起点；只展示成功截图无法说明动作确实来自工具观察。
5. 提交质量不仅取决于测试数量，目录、运行命令、实际输出、Trace 和限制披露同样是验收的一部分。

## 4. 做得较好的部分

- 正常、超预算、永久工具失败和无可行方案均有明确终态，失败历史与已成功结果不会被后续方案覆盖。
- 费用分项、沉没费用、截止时间和保存依赖由程序测试，而非只写在提示词中。
- 离线替身与真实模型证据明确分开，保留真实模型失败及提示修改过程。
- 通过 SQLite 回执和唯一约束验证重复提交、恢复和重复工具调用不会重复收费。

## 5. 未完成与下一步

1. 增加更大规模、固定条件的真实模型回归，不把当前小样本成功率外推。
2. 若接真实外部工具，增加供应商幂等键、结果查询和未知账单对账，而不是沿用本地纯函数假设。
3. 增加 `graph_schema_version`、工具契约版本与明确迁移策略，而不只依赖运行时一致性检查。
4. 引入精确 tokenizer，以及人工内容质量和版权审核环节。
